## Trigger: "neovim news daily"

When the user says **"neovim news daily"** (or close variants), run this update procedure directly — no need to ask for confirmation first:

1. Run `nvim --version` to get the currently installed build's commit SHA. Compare it to the `Baseline checked` line below.
2. Fetch `https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/news.txt` and check the "NVIM v0.13" (or current unreleased) section for entries not already represented in the table below.
3. Fetch recent `neovim/neovim` master commits (e.g. `gh api repos/neovim/neovim/commits?sha=master --paginate` or the commits web UI) covering the range between the old `Baseline checked` SHA and the current installed build's SHA. Skip anything already referenced by SHA in an existing row or in the "Already adopted" / "Lower-signal entries skipped" notes.
4. For each genuinely new item (news.txt entry or commit), cross-reference it against this repo's actual Neovim config — `nvim/.config/nvim/lua/user/*.lua`, `nvim/.config/nvim/lua/plugins/*.lua`, `options.lua`, `keymaps.lua`, `autocommands.lua`, etc. — and decide relevance the same way existing rows do: cite specific file:line evidence, state what was actually checked/verified (not just described), and prefer default `skip`/`implement` over `pending` unless real interactive testing is required.
5. Append new rows to the table, continuing the `#` numbering — never edit or renumber existing rows, and never change a `Decision` that's already `implement` or `skip`. If a row was `pending` and can now be resolved (e.g. row 15's `nvim.dir` vs nvim-tree race), verify and resolve it rather than leaving it stale.
6. Update the `Baseline checked` and `Generated` lines at the top to reflect the new build/date once the update is complete.
7. If nothing new is found, still update `Baseline checked`/`Generated` and say so briefly — don't leave the doc looking unchecked.
