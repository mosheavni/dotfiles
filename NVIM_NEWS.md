## Trigger: "neovim news daily"

When the user says **"neovim news daily"** (or close variants), run this update procedure directly — no need to ask for confirmation first:

1. Run `nvim --version` to get the currently installed build's commit SHA. Compare it to the `Baseline checked` line below.
2. Fetch `https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/news.txt` and check the "NVIM v0.13" (or current unreleased) section for entries not already represented in the table below.
3. Fetch recent `neovim/neovim` master commits (e.g. `gh api repos/neovim/neovim/commits?sha=master --paginate` or the commits web UI) covering the range between the old `Baseline checked` SHA and the current installed build's SHA. Skip anything already referenced by SHA in an existing row or in the "Already adopted" / "Lower-signal entries skipped" notes.
4. For each genuinely new item (news.txt entry or commit), cross-reference it against this repo's actual Neovim config — `nvim/.config/nvim/lua/user/*.lua`, `nvim/.config/nvim/lua/plugins/*.lua`, `options.lua`, `keymaps.lua`, `autocommands.lua`, etc. — and decide relevance the same way existing rows do: cite specific file:line evidence, state what was actually checked/verified (not just described).
   - **Don't assume the user's preference. Auto-decide `skip`/`implement` only for facts** — a bug that's clearly irrelevant (feature isn't used, code path doesn't exist), or a pure upstream bugfix with zero config surface (applies automatically, no tradeoff). Cite the evidence that makes it a fact, not a guess.
   - **Anything with a tradeoff, an opt-in behavior change, or more than one reasonable way to adopt it is a `pending` row — surface it as a question (e.g. via AskUserQuestion) instead of deciding for the user.** This includes: new keybinding defaults that could go multiple ways, features that reshape existing behavior (even if "probably fine"), and anything where the write-up would otherwise need the word "likely wants" or "probably doesn't need." When in doubt, ask rather than assume.
   - Follow through on `pending` answers immediately: if the user picks an option that touches other config (e.g. a keymap collides with something else, like `gq` already being wired to `conform.nvim`'s `formatexpr`), surface that collision and re-ask rather than silently implementing the collision.
   - **`news.txt`/`repeat.txt`/etc. are fetched live from GitHub's `master` branch — they can describe behavior that hasn't actually landed in the locally installed nightly yet.** Before declaring a builtin-default behavior change "already live, nothing to do," verify against the *actual installed build*: `:verbose <map-command> <key>` for keymap defaults, or read the real file under `$VIMRUNTIME` (e.g. `$VIMRUNTIME/lua/vim/_core/defaults.lua`) directly — don't trust the fetched doc's prose alone. Row 21's `Q`-multicursor mistake was exactly this: docs described the target behavior, but this build's shipped `defaults.lua` still had the old mapping.
5. Append new rows to the table, continuing the `#` numbering — never edit or renumber existing rows, and never change a `Decision` that's already `implement` or `skip`. If a row was `pending` and can now be resolved (e.g. row 15's `nvim.dir` vs nvim-tree race), verify and resolve it rather than leaving it stale.
6. Update the `Baseline checked` and `Generated` lines at the top to reflect the new build/date once the update is complete.
7. If nothing new is found, still update `Baseline checked`/`Generated` and say so briefly — don't leave the doc looking unchecked.
